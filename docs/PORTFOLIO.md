# Portfolio presentation

## One-line summary

A production-oriented C++/Python release engineering lab that turns one SemVer
tag into tested manylinux wheels, an Ubuntu DEB, and a non-root OCI image with
checksums, SBOM, provenance, security policy enforcement, rollback controls,
and disaster-recovery proof.

## Engineering decisions worth discussing

| Decision | Why it matters | Evidence |
| --- | --- | --- |
| One tag owns the release | Prevents independent workflows from publishing inconsistent versions | `release.yml`, version and CHANGELOG gate |
| Build once, verify before publish | Rejects missing native extensions, broken DEB metadata, and unhealthy containers | installed-wheel, external CMake consumer, and runtime smoke tests |
| Digest is the rollback identity | Mutable aliases can move without altering historical artifacts | rollback workflow and runbook |
| Evidence is bound to artifacts | Checksums alone prove integrity, while attestations connect artifacts to the build identity | SBOM and provenance verification |
| Policy becomes a required check | Vulnerability and license decisions block merges and releases instead of living only in prose | `Security gate` and release preflight |
| Recovery is continuously tested | Retention is useful only when preserved artifacts can be rehydrated | monthly DR workflow and final rehearsal |

## Architecture narrative

The codebase deliberately separates three consumer surfaces: a native CMake
package, Python wheels containing a pybind11 extension, and a minimal container
CLI. Compatibility testing operates on installed outputs rather than only on
the source tree. The tag-driven release waits for the exact commit's security
gate, assembles all artifacts, emits SPDX and SHA-256 evidence, attaches GitHub
artifact attestations, publishes a draft, then verifies the immutable release.

Operational workflows keep the release immutable. Rollback moves only floating
container aliases after an approval gate, retention policy is machine-audited,
and disaster recovery downloads the public release into a clean directory and
tests the container by digest. The final rehearsal repeats this consumer path
and generates a report from live GitHub API data.

## Interview demo (five minutes)

1. Open the public release and show the wheel, DEB, SBOM, checksums, and digest.
2. Open the successful unified release run and trace the dependency graph.
3. Run `gh release verify` and one `gh attestation verify` command.
4. Open the final rehearsal report and its clean-room recovery PASS results.
5. Explain why the rollback moves aliases instead of changing release assets.

after the live rehearsal passes. Do not claim production traffic, user scale,
performance gains, or incident recovery time: this laboratory demonstrates
release-system design and verified execution, not those outcomes.

## Verified v0.1.0 release

The public [v0.1.0 release](https://github.com/vonbraunpark/furiosa-build-release-lab/releases/tag/v0.1.0) contains Python 3.10–3.13 manylinux wheels, an Ubuntu DEB, an SPDX SBOM, and SHA256 checksums. The container is published by digest.

The [final release rehearsal](https://github.com/vonbraunpark/furiosa-build-release-lab/actions/runs/36389229608) completed successfully. Its generated evidence records an immutable release, a passing security gate, and a passing clean-room recovery from public artifacts. The recovery report records passing asset integrity, checksum, provenance and SBOM attestation, SPDX structure, and container smoke-test checks.

This evidence applies to the v0.1.0 release and the linked rehearsal run. It does not claim production adoption or availability.
